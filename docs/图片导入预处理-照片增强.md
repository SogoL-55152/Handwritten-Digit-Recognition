# 图片导入的照片增强（白底黑字 + 加粗）

> 2026-11-12。图片导入路径在送模型前先做一次照片增强：**光照归一化 → Otsu 二值化 → 加粗**，把灰纸、阴影、纸纹压成白底黑字的干净输入。画板路径不变。

## 1. 为什么需要

画板输入本身是干净的（白底、固定线宽），而照片有三类干扰：

| 干扰 | 后果 |
|---|---|
| 光照渐变/阴影 | 阴影被当成一大片墨迹，数字被"吃掉" |
| 纸面纹理与底色 | 前景阈值波动，笔画断裂或粘连 |
| 笔画偏细 | 与训练时的画板线宽不匹配，逐字准确率下降 |

## 2. 处理流程

```
上传 JPEG/PNG
  → gray_from_payload      解码、EXIF 方向校正、白底合成（CMYK/ICC 也在这里处理）
  → 反相判断               median < 128 视为白字黑底，先取反
  → 背景估计               大半径高斯模糊（半径 = 短边/12，远大于笔画宽度）
  → 光照归一化             norm = gray / background × 255
  → Otsu 阈值              直方图类间方差最大化
  → 墨迹掩膜               取反得到"True = 墨迹"，前景占比 >60% 时再取反一次
  → 闭运算 + 加粗          先 dilate 填孔、再 erode，然后按短边比例 dilate 1–4 次
  → 白底黑字               ink ? 0 : 255
```

加粗幅度按图片短边缩放：`max(1, min(4, round(短边 × 0.006)))`，即小图 1px、手机照片 3–4px。上限 4px 是为了不把 `1` 和 `7` 的拐角糊在一起。

## 3. 只有图片导入走

- 前端：`recognize(..., { enhance: true })` 在图片模式加 `?enhance=true`；画板模式不加；
- 后端：只允许 `enhance=true|false` 这一个查询参数，其他查询串一律 400；
- 模型服务：`enhance=1` 时才调用 `enhance_photo`。

多位数识别在图片模式下同样走这条增强（/recognitions/multi?enhance=true）。

这样 **画板路径的既有行为完全不变**（已有 19/18/11/13 项联调依赖它）。

## 4. 页面上的可见效果

图片模式下「移除图片」旁边有「**查看预处理效果**」按钮：点开显示预处理后的图（白底黑字、笔画加粗），并注明"实际送入模型的就是这张"。

接口：`POST /api/v2/workspaces/{wid}/recognitions/preview-image`（multipart，返回 `image/png`，不落库、不计数）。

## 6. 顺带修掉的一个真问题

这些照片里有 **CMYK/带 ICC 的 JPEG**，而本机 JDK 缺 `lcms` 原生库，`ImageIO` 一解码就抛 `UnsatisfiedLinkError`（之前表现为"服务暂时异常"）。

现在 `ImageValidator` 在遇到 `LinkageError` 时**不再拒绝**：只校验容器格式与文件大小，把尺寸上限、空白判定、内容合法性交给模型服务（Pillow 不依赖 lcms）。这样：
- 这类照片能正常进入识别流程；
- 空白图仍会被模型服务拒绝（400 `BLANK_IMAGE`）；
- 不需要重装 JDK。

## 7. 已知限制

- 9 这类照片仍然认错——增强改善输入，不提升模型对照片域的表达能力，需要微调；
- Otsu 是全局阈值，极端光照（强反光、半张纸在阴影里）仍可能失败；
- 加粗是固定形态学膨胀，笔画粗细差异很大的书写可能被统一化；
- 没有做透视/旋转矫正（拍歪的照片仍按原样处理）；
- 预览按钮是手动触发，不会随选图自动刷新。
