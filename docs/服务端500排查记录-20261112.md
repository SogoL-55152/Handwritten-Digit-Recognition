# 服务端 500 排查记录（2026-11-12）

## 现象

导入图片点「识别图片」后，右侧显示：

> 服务暂时异常，请稍后重试

前端没有更多信息，页面同时出现「这次没有给出结果。你实际写的是几？」（因为识别确实失败了）。

## 这条文案意味着什么

它来自后端兜底处理器 `V2ExceptionHandler.unexpected()`：

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<?> unexpected(Exception error, HttpServletRequest request) {
    LOG.error("V2 request failed: {}", error.getClass().getSimpleName());
    return business(new V2Exception(500, "服务暂时异常，请稍后重试", "INTERNAL_ERROR"));
}
```

所以它是**后端未捕获异常的兜底 500**，不是模型服务不可用——后者会返回 502/503，文案是「识别或基础服务暂不可用」。

## 当时能拿到的线索

日志（`D:\Temp\hdr-run\backend.out.log`）只有三行，**没有堆栈**：

```
12:15:18.453 ERROR ... V2ExceptionHandler : V2 request failed: ServletException
12:15:20.167 ERROR ... V2ExceptionHandler : V2 request failed: ServletException
12:15:22.534 ERROR ... V2ExceptionHandler : V2 request failed: ServletException
```

间隔约 2 秒，符合"用户连续点了三次识别"。异常类型是 `jakarta.servlet.ServletException`，而模型调用失败的路径已被 `ModelClient` 映射成 502/503，不会落到这里。

## 最可能的原因

**multipart 请求解析失败**。当时配置是 `file-size-threshold` 默认值 `0`，意味着**每一张上传图片都会先写到 Tomcat 临时目录**（`%TEMP%`，本机为 `D:\Temp`）。这台机器上安全软件会占用/清理临时文件——同一台机器上 `vite build` 的 esbuild 就是因为临时文件被占用而失败（`Access is denied`）。

图片只有 17 KB，本来完全不需要落盘；一旦临时文件被占用，解析失败就会以 `ServletException` 冒到兜底分支，被翻译成"服务暂时异常"。

## 已做的三处修复

| 修复 | 位置 | 作用 |
|---|---|---|
| 小图不落盘 | `application.yml`：`spring.servlet.multipart.file-size-threshold: 1MB` | 1 MB 以内的图片留在内存，不依赖临时目录（用户的 17 KB 图片属于此类） |
| 解析失败给明确错误 | `V2ExceptionHandler`：新增 `MultipartException` → 400 `UPLOAD_PARSE_FAILED`「图片上传解析失败，请重试或换一张图片」 | 同类问题不再显示成"服务暂时异常"，也便于区分 |
| 500 记录完整堆栈 | `V2ExceptionHandler.unexpected()` 改为 `LOG.error(msg, error)` | 下次真的 500，日志里直接有堆栈，不用再猜 |

## 验证

改完后用与用户图片同规格的 JPEG（732×562，JPEG，约 17 KB）连续识别 5 次：

```

1 200 digit=1 ...
2 200 ...
3 200 ...
4 200 ...
```

后端日志无新增 `V2 request failed` / `multipart parse failed`。后端单测 156 项通过。

## 以后再遇到怎么看

1. `D:\Temp\hdr-run\backend.out.log` 搜 `V2 request failed`（现在带堆栈）；
2. 若出现 `multipart parse failed` → 上传解析问题，多半还是临时目录/临时文件被占用；
3. 若是 `MODEL_UNAVAILABLE`（502/503）→ 看模型服务 `/api/v1/health` 与 `weights/registry.json` 是否完整；
4. 若是 `DATABASE_UNAVAILABLE`（503）→ MySQL 是否在跑。

## 遗留

- 根因未能 100% 坐实（当时没有堆栈），只能说是"最可能"。如果复现，现在日志里有堆栈，可以直接定位。
- 大于 1 MB 的图片仍然会落临时文件；若再次出现同类问题，可把 `spring.servlet.multipart.location` 指到一个不在安全软件扫描范围内的目录。
