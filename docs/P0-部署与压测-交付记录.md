## 4. 压测结果（P0-5 / P0-6）

### 4.1 纯推理容量（`--mode model`，直连 5001，绕过网关限流）

| 指标 | 数值 |
|---|---|
| 并发 / 时长 | 4 / 30 s |
| 成功请求 | 553（18.4%），其余 2451 返回 **429** |
| 吞吐 | **18.4 成功 req/s**（≈1106/分钟） |
| 延迟（成功） | 平均 116.5 ms · P50 117.2 · **P95 145.3** · P99 170.3 · max 187.0 |

> 模型服务**只有 2 个有界推理槽**（`serve.py` 的 4 线程 + 内部信号量），单次推理 ~110–120 ms，
> 因此容量约 2 ÷ 0.117 s ≈ **17–18 req/s**；超过就立刻 429（明确背压，不会排队堆积）。

### 4.2 端到端识别（`--mode backend`，走完整网关链路）

| 轮次 | 账号数 | 成功 | 429 | 吞吐 | 延迟（成功） |
|---|---|---|---|---|---|
| 第 1 轮 60 s / 并发 4 | 3 | 97 | 13985 | 1.62 req/s | P50 160.6 ms · P95 184.8 ms |
| 第 2 轮 60 s / 并发 4 | 1 | 51 | 15768 | 0.85 req/s | P50 107.2 ms · P95 139.4 ms |

> **结论：端到端吞吐不是被推理能力卡住，而是被设计限流卡住。**
> - 每用户 `W2_RECOGNITION_PER_MINUTE` 默认 **60 次/分钟**（1 req/s）；
> - 全局 `limiter.check("recognition:global", 240, 60)` **写死在 `RecognitionService`**，即全平台 **240 次/分钟（4 req/s）**；
> - 注册接口另有按 IP 限流，压测脚本无法快速造出多个账号（第 2 轮只拿到 1 个账号，成功率更低）。
> - 超限一律 429，**没有出现任何 5xx**——限流层是有效的过载保护。
> - 单次成功识别（含网关鉴权、限流、落库、模型调用）P95 ≈ 139–185 ms，其中模型推理约 117 ms，网关开销约 20–70 ms。

若要真正压容量，需要先调整三处阈值（建议做成配置项而非硬编码），再按"每用户 60/min × 用户数 vs 全局 240/min"估算。

### 4.3 训练并发（P0-6）

`--pool=solo` 的 worker 一次只跑一个任务，因此加 worker 数量是唯一扩并发手段。

| 场景 | 任务 | 排队 | 执行 | 墙钟合计 |
|---|---|---|---|---|
| 1 个 worker | task 4 | 0 s | 96 s | **184 s** |
| | task 5 | **97 s** | 87 s | |
| 2 个 worker | task 6 | 0 s | 88 s | **96 s** |
| | task 7 | **0 s** | 96 s | |

> 结论：**第 2 个 worker 把排队时间从 97 s 降到 0 s，并把 2 个任务的墙钟时间从 184 s 压到 96 s（吞吐 ≈ 2×）。**
> 代价是需要独立 Redis 隔离压测环境（任务书第 10 节已提醒），否则压测任务会被生产 worker 抢走。

## 10. 收尾过程中发现的缺陷：训练版本号与发布基线撞名（已加护栏）

### 现象与现场

在跑训练回归时提交了第 8 个训练任务，任务**永久停在 RUNNING**，worker 日志末尾是：

```
RuntimeError: callback failed: 500 {"code":500,"message":"服务暂时异常","data":{"category":"INTERNAL_ERROR"}}
```

后端日志给出了真正原因：

```
org.springframework.transaction.UnexpectedRollbackException:
  Transaction rolled back because it has been marked as rollback-only
  at com.hdr.v2.training.TrainingService.applyState(...)
  at com.hdr.v2.training.InternalTrainingController.state(InternalTrainingController.java:46)
```

进一步检查发现**发布基线被训练产物覆盖了**：

| 项 | 训练前 | 训练后 |
|---|---|---|
| `weights/w4-train/8/checkpoint.pt` | `b117effe…`（Release 基线，1,689,920 B） | `beef639e…`（1000 样本 1 轮训练结果，1,690,679 B） |
| `registry.json` 中的 `w4-task-8-a1` | 指向发布基线摘要 | 被替换为训练结果摘要 |
| 数据库 `t_v2_model.sha256` | `b117effe…` | 仍是 `b117effe…` → **与注册表不一致** |

后果：模型管理里该模型变成 `verified=false`，无法再激活；如果它当时不是生效模型，识别会直接失败。

### 根因

1. 训练产物版本号规则是 `w4-task-<taskId>-a<attempt>`，而 `weights-v1` 发布基线刚好叫 `w4-task-8-a1`
   → **任何任务 id 递增到 8 的部署都会命中**。
2. `training_tasks.py::_publish_registry` 旧实现按版本号**直接替换**条目，没有防覆盖判断。
3. 后端 `TrainingService.applyState` 在注册新模型时抛错，异常被内层事务标记 rollback-only，
   外层提交时变成 `UnexpectedRollbackException` → 回调 500 → 任务卡在 RUNNING（租约到期才回收）。

### 本次处理

| 动作 | 说明 |
|---|---|
| 恢复基线 | `scripts/fetch-weights.ps1 -ForceRegistry` 重新下载并写回 `registry.json`；文件、注册表、数据库三处摘要一致（`b117effe…`） |
| 重载注册表 | `POST /api/v2/admin/models/registry/reload`，模型服务缓存刷新 |
| 复核识别 | 5/5 正确（`modelVersion=w4-task-8-a1`） |
| 清理僵尸任务 | 手工把 task 8 落成 `FAILED`（`error_category=CALLBACK_FAILED`） |
| **加护栏** | `_publish_registry` 现在拒绝覆盖"同名但摘要不同"的条目，抛 `模型版本 X 已登记为其它产物…训练结果不会覆盖已发布模型`；新增 3 个单测（`model-service/tests/test_publish_registry.py`） |

### 建议的彻底修复（进 P1）

1. **版本号加命名空间**：训练版本改成带时间戳/随机后缀（如 `w4-task-8-a1-20261125T1830`），彻底避开与发布基线撞名。
2. **后端注册失败不污染事务**：`applyState` 里注册模型改用独立事务或"先查后插"，避免 `UnexpectedRollbackException` 变成 500。
3. **worker 回调失败要落终态**：`notify` 抛错时把任务写成 FAILED 并带原因，不要让任务卡在 RUNNING 等租约回收。
4. **发布基线改名**：若继续用 `weights-v2`，建议把基线版本号改成不含 `task` 的形式（如 `baseline-canvas-photo-v2`），从命名上隔离两类模型。
