# 导入异步化（后台任务 · 进度 · 取消）

> 对应交接文档 P1-10：「导入异步化（后台任务 + 进度 + 取消）——大 zip currently 同步等待」
> 完成日期：2026-11-25

---

## 1. 改动前

`POST /datasets/{id}/import-wizard`（以及 `zip`、`upload-commit`）在**请求线程里**做完所有事：
扫描目录 → 逐张读图 → 算摘要 → 写采集库 → 更新批次，全部包在一个事务里。

1500 张大约 40–60 秒，20000 张（`MAX_FILES`）远超任何反向代理/浏览器超时；
一旦超时，前端只知道"失败了"，**看不到导入到哪一步、也没法停**。

## 2. 现在的设计

### 2.1 任务表（迁移 V22）

```sql
CREATE TABLE t_import_job (
  id, workspace_id, dataset_id,
  source_kind,            -- DIRECTORY / ZIP / UPLOAD
  directory,              -- 绝对路径；ZIP/UPLOAD 结束后删除
  file_column, label_column,
  cleanup,                -- 1=任务结束后删除 directory
  status,                 -- QUEUED / RUNNING / SUCCEEDED / FAILED / CANCELED
  progress_total, progress_done, imported, duplicates, failed,
  error_message, import_batch_id, cancel_requested,
  created_by, created_at, started_at, finished_at
)
```

`import_batch_id` 指向既有的 `t_import_batch`：**回滚仍然走原来的批次回滚接口**，没有第二套回滚逻辑。

### 2.2 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/datasets/{datasetId}/import-jobs` | `{directory \| token, sourceKind, fileColumn, labelColumn}` → 立即返回任务 |
| GET | `/import-jobs/{jobId}` | 状态、进度、计数、错误、批次号 |
| POST | `/import-jobs/{jobId}/cancel` | 协作式取消 |
| GET | `/import-jobs?limit=10` | 最近任务 |

原来的同步接口（`import-wizard`、`import-wizard/zip`、`upload-commit`）**保留不动**，脚本与旧客户端不受影响。

### 2.3 执行

- 后端内 `ThreadPoolExecutor(2 线程, 队列 32)`；队列满 → `429 IMPORT_QUEUE_FULL`，任务行直接落 `FAILED` 并写明原因，不会让前端一直等。
- 任务线程里先 `prepare`（校验 + 扫描 + 建批次）→ 回写 `progress_total` → 再 `runPrepared` 逐张导入。
- **扫描期间 `progress_total=0`**，前端显示"正在扫描目录…"，扫描完成后变成"正在导入 x / y 张"。
- 每 25 张写一次 `progress_done`；每张图之前检查一次取消标记，**标记读取有 1 秒缓存**（否则 2 万张就是 2 万次查询）。
- 取消：`QUEUED` 直接落 `CANCELED`；`RUNNING` 置标记后由循环在下一个文件前停下，**已导入的部分保留**（可回滚）。
- `ZIP` / `UPLOAD` 的临时目录在 `finally` 里删除，无论成功、失败还是取消。

### 2.4 前端

`Datasets.vue` 的三个入口（服务器目录 / zip / 上传文件夹）统一改成：创建任务 → 每秒轮询 → 进度条 + 计数 → 可取消；终态后刷新数据集与批次列表。纯逻辑抽到 `frontend/src/datasets/job.js`（百分比、状态文案、是否可取消）以便单测。

端到端（真实接口）：

| 场景 | 结果 |
|---|---|
| 10 张目录 → 任务 | 创建即返回 `QUEUED`；终态 `SUCCEEDED`，`imported=10`，`progress 10/10`，带 `importBatchId` |
| 1350 张目录 → 跑到 50 张时取消 | `CANCELED`，`imported=98`（取消生效在 1 秒内），`progress_done=108/1350` **不会跳到 100%**，批次 #13 仍可回滚 |
| 非法 `sourceKind=SFTP` | `400 VALIDATION` |
| 不存在的任务 | `404 JOB_NOT_FOUND` |
| zip 上传 → 异步任务 | `SUCCEEDED`，`imported=10`，**任务结束后临时目录已删除**（复检 `exists()=False`） |

## 4. 已知局限（重要）

1. **单实例内存队列**：任务只在提交它的那个后端实例上执行。多实例部署时任务表仍可查，但另一台实例不会接手；
   进程重启会丢失 `QUEUED/RUNNING` 的任务（表里会留下 RUNNING 的僵尸行）。
   要真正多实例，得把任务投递到 Celery 或引入外部队列——这属于部署架构决定，不在本次范围。
2. **不做断点续传**：取消后没有"从第 N 张继续"的能力，只能重新导入（重复样本会被去重）。
3. **进度粒度是每 25 张**，因此小批量（<25 张）只会看到 0 → 完成两跳。
4. **扫描阶段没有进度**：目录很大时"正在扫描"可能停留几十秒（扫描本身要遍历文件）。
5. **同步接口仍在**：若继续调用旧接口，仍是同步阻塞行为；前端已全部切到任务接口。
