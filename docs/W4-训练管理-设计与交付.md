# W4 训练管理：队列机制设计与验收

> 2026-11-08。Sprint 目标：模型训练管理（选数据集、配参数、发起训练），里程碑 M2「训练可跑通并保存模型」。
> 本页记录队列架构、四项断言的实测证据、以及**明确不作高可用依据**的生产层限制。

## 1. 架构与链路

```text
管理员 → Java  POST /api/v2/admin/training/tasks
           │  ① 参数校验 + 落库 QUEUED（t_v2_training_task）
           │  ② 调 Python /internal/v2/training 入队，拿 Celery 任务 ID
           ▼
        Celery worker（solo 池，-Q training）
           │  ③ 开跑：回调 Java RUNNING（attempt 来自 Redis 原子计数）
           │  ④ 训练：复用 train_canvas_aug（线上 canvas_input 同源）
           │  ⑤ 产物落到 weights/w4-train/<taskId>/checkpoint.pt，服务端算摘要
           │  ⑥ 写 registry.json 新条目
           ▼
        Java  POST /internal/v2/training/{id}/state（内部令牌）
           │  ⑦ 状态/指标/产物回写；逐轮指标写 t_v2_training_metric
           │  ⑧ 复用 W3 登记接口把产物登记为模型（INACTIVE，激活仍需管理员）
           ▼
        前端/接口随时查询任务详情
```

数据库是唯一事实来源；Python 不直连 MySQL，全部通过回调写回。

## 3. 四项断言的实测证据

脚本：`.git/w2-local/w4-queue-smoke.py`（真实 Redis + 真实 worker + 真实 Java + 真实训练，1000 样本 1 轮）。运行结果 **11 项全部通过**：

| 项 | 断言 |
|---|---|
| **入队** | 创建接口返回 `QUEUED` + Celery 任务 ID；worker 尚未启动时 `LLEN training >= 1` |
| **消费** | worker 取到任务 → `RUNNING` 且 `attempt=1` → 最终 `SUCCEEDED`，`startedAt/finishedAt` 完整 |
| **结果回写** | 产物路径、64 位 sha256、大小落库；`metrics.history` 逐轮指标存在；产物已登记为模型且 `INACTIVE`、`verified=true`、摘要与任务行一致 |
| **崩溃重投** | 任务运行中 `taskkill /F` 硬杀 worker → 租约过期 → 任务被重新入队 → 新 worker 跑完 → `SUCCEEDED` 且 **attempt=2**，重投产物同样登记为模型 |

样例输出：

```json
{"checks": 11, "queue": "training", "leaseSeconds": 30,
 "firstTask": {"id": "4", "version": "w4-task-4-a1"},
 "redelivered": {"id": "5", "attempt": 2, "version": "w4-task-5-a2"}}
```

## 4. 崩溃重投：为什么用租约而不是 broker 的 visibility_timeout

实测结论（kombu 5.4 / Redis 5 / Windows 硬杀）：

- `kombu.transport.redis.QoS.restore_visible(interval=10)` 只在**每 10 次调用**时才真正恢复未确认消息；worker 冷启动后 `on_poll_init` 只调用一次，计数为 0 时直接返回，因此**硬杀场景下消息不会被恢复**，任务会永久停在 RUNNING。
- 优雅退出（`task_reject_on_worker_lost`）在 Windows 上拿不到 SIGTERM，`taskkill` 不带 `/F` 也无法送达，因此不可依赖。

所以本实现用**应用层租约**达到同样的语义，并且可断言：

1. 入队时把参数快照写 Redis（`training:payload:<id>`）并加入活跃集合 `training:active`；
2. 任务开始执行时写租约 `training:lease:<id>`（TTL 30s），运行期间**心跳每 10s 续租**；
3. worker 被硬杀 → 心跳消失 → 租约 30s 后自然过期；
4. 任意存活 worker 的 reaper（每 3s 一次，`worker_ready` 时启动，仅 worker 进程）发现"活跃集合里有、但租约已过期、且有参数快照"的任务，用 `SET NX` 抢锁后重新 `apply_async`；
5. 重投后 `attempt` 由 Redis 原子计数递增（`INCR`），因此任务行显示 `attempt=2`，不会被伪装成第一次。

失败任务不会重投：显式 `FAILED` 回调后会清理活跃集合与参数快照。

## 5. 生产层限制（不作为高可用依据）

- Windows + `solo` 池 + 二进制 Redis 只证明**机制可用**，**不证明**高可用、吞吐、跨机容灾、消息持久化承诺。
- 单 worker 单并发；多 worker 并发、托管 broker（如云 Redis/Kafka/RabbitMQ）、消息持久化与告警，**留到 Compose/Linux 阶段**另行验证与记录。
- 本地 Redis 关闭了 RDB/AOF，进程重启会丢未完成队列（活跃集合在 Redis 里，也会丢）；任务行仍留在 MySQL，但不会被自动重投。这是本地演示的取舍。

## 7. 接口

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/v2/admin/training/tasks?limit=` | SUPER_ADMIN | 任务列表 |
| `GET /api/v2/admin/training/tasks/{id}` | SUPER_ADMIN | 任务详情（含 metrics） |
| `GET /api/v2/admin/training/tasks/datasets` | SUPER_ADMIN | 可选数据集（仅元数据） |
| `POST /api/v2/admin/training/tasks?datasetId=` | SUPER_ADMIN | 创建并入队；入队失败落 FAILED 并返回 503 |
| `POST /internal/v2/training/{id}/state` | 内部令牌 | Python 回调（RUNNING/SUCCEEDED/FAILED） |
